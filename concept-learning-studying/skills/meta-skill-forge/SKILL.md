# 메타 스킬 포지 (Meta-Skill Forge)

## 이 스킬의 목적

사용자가 새로운 스킬을 만들고 싶을 때, 단순한 지시문 모음이 아니라
**사용자의 암묵적 전문성이 녹아든 사고 시스템**을 설계하도록 돕는다.

핵심 원칙: 스킬은 AI에게 "무엇을 하라"가 아니라 "어떻게 생각하라"를 가르치는 것이다.

---

## 워크플로우 개요

7개 단계를 순서대로 진행한다. 각 단계는 반드시 눈에 보이는 산출물을 만든다.
산출물이 없는 단계는 존재할 이유가 없다.

| 단계 | 이름 | 산출물 |
|------|------|--------|
| 1 | 게으른 버전 체험 | baseline 결과물 + 불만 목록 |
| 2 | 암묵지 발굴 | 사용자 전문성 문서 |
| 3 | 반대로 설계 (Contrarian Frame) | 금지 패턴 목록 + 차별화 방향 |
| 4 | 아키텍처 결정 | 파일 구조 설계도 |
| 5 | 스킬 작성 | SKILL.md + 참조 파일들 |
| 6 | 검증 | 리뷰 프레임워크 점검 결과 |
| 7 | 배포 | 완성 패키지 |

---

## 단계 1: 게으른 버전 체험

스킬을 한 줄도 쓰기 전에, AI가 아무 지시 없이 해당 작업을 하면 어떤 결과가 나오는지 확인한다.
이것이 앞으로 모든 개선의 기준점(baseline)이다.

### Claude가 할 일

사용자에게 다음을 요청한다:

> "만들고 싶은 스킬이 처리할 작업을 하나만 구체적으로 알려주세요.
> 예: '3학년 나눗셈 학습지 만들기', '이번 주 경제 뉴스 브리핑'
> 제가 먼저 아무 스킬 없이 그냥 해보겠습니다."

그 다음 스킬 없이 작업을 수행하고, 결과를 보여주면서 묻는다:

> "이 결과에서 **구체적으로 마음에 안 드는 점**을 모두 말씀해주세요.
> '별로다'는 안 됩니다. '문제 난이도 차이가 없다', '모든 문장이 ~합니다로 끝난다'
> 수준으로 구체적이어야 합니다."

### 산출물

- baseline 결과물 (파일 또는 텍스트)
- 사용자의 불만 목록 (최소 5개, 구체적일수록 좋다)

불만이 5개 미만이면 추가 질문으로 끌어낸다:
- "이 결과를 동료 교사에게 보여줄 수 있나요? 부끄러운 부분이 어디인가요?"
- "학생/학부모가 이걸 보면 어떤 반응일까요?"
- "이 결과에서 '아, AI가 만들었구나' 티가 나는 부분은요?"

---

## 단계 2: 암묵지 발굴

사용자가 해당 작업을 직접 할 때의 무의식적 판단을 글로 꺼낸다.
이것이 스킬에 녹여야 할 핵심 재료다.

### Claude가 할 일

4라운드로 질문한다. 단, 이전 대화에서 이미 답이 나온 항목은 건너뛴다.
질문지를 기계적으로 읽지 않는다. 대화하듯 자연스럽게 진행한다.

**라운드 1 — 범위:**
- 이 작업을 할 때 가장 먼저 하는 행동은 무엇인가요?
- 이 작업의 결과물을 누가 보나요? (학생? 학부모? 본인?)
- "잘된 결과물"의 구체적 특징을 3개만 말해주세요.

**라운드 2 — 차별화:**
- 이 작업에서 AI가 가장 못하는 부분은 뭐라고 생각하세요?
- 경력 있는 교사와 신규 교사의 결과물 차이는 어디서 드러나나요?
- 이 작업에서 절대 하면 안 되는 실수는?

**라운드 3 — 구조:**
- 고정된 템플릿이 있나요, 매번 다르게 하나요?
- 외부 자료(교육과정, 교과서, 뉴스 등)를 참조해야 하나요?
- 결과물의 형식은? (문서? 표? 프레젠테이션?)

**라운드 4 — 극한 상황:**
- 이 스킬이 완전히 엉뚱한 결과를 낼 수 있는 입력은?
- 이 스킬이 명시적으로 거부해야 할 요청이 있나요?

### 산출물

사용자 전문성 문서: 위 질문들의 답을 구조화한 것.
이 문서는 이후 모든 단계의 기초 자료가 된다.

---

## 단계 3: 반대로 설계 (Contrarian Frame)

단계 1의 baseline 결과물을 분석하여, AI의 기본 행동에서 벗어날 방향을 설계한다.

### Claude가 할 일

baseline 결과물에서 다음을 추출한다:

1. **예측 가능한 구조**: AI가 기본으로 선택한 구성 방식
   - 예: 항상 "정의 → 설명 → 예시 → 정리" 순서
2. **반복되는 표현**: AI가 좋아하는 단어와 문장 패턴
   - 예: "~에 대해 알아봅시다", "~할 수 있습니다", "다양한", "효과적인"
3. **숨은 가정**: AI가 묻지 않고 전제한 것들
   - 예: 모든 학생이 같은 수준이라는 가정

이 분석 결과를 사용자에게 보여주고 함께 금지 패턴 목록을 만든다.

### 산출물

**금지 패턴 목록** (세 범주):
- 금지 표현: 출력에 절대 포함되면 안 되는 단어/문구
- 금지 구조: 피해야 할 구성 패턴
- 금지 가정: 묻지 않고 전제하면 안 되는 것들

**차별화 방향 선언문**: 한 문단으로, "이 스킬의 결과물은 ___와 같고, ___와 같지 않다"

---

## 단계 4: 아키텍처 결정

스킬의 파일 구조를 결정한다. 과도하게 복잡하게 만들지 않는다.

### 판단 기준

다음 질문에 순서대로 답한다:

**Q1. 작업이 하나인가, 여러 개인가?**
- 하나 → 단일 파일 (300줄 이하)
- 여러 개 → 모듈형

**Q2. 도메인 지식이 얼마나 필요한가?**
- 최소 → 메인 파일에 포함
- 보통 → references/ 폴더에 분리
- 많음 → references/를 하위 주제별로 분리

**Q3. 예시가 필요한가?**
- 좋은 예시 + 나쁜 예시 쌍이 3개 이상 필요하면 별도 파일로

**Q4. 금지 패턴이 20개 이상인가?**
- 예 → references/anti-patterns.md로 분리
- 아니오 → 메인 파일에 포함

### 산출물

파일 구조 설계도 예시:
```
skill-name/
├── SKILL.md              ← 라우터 + 핵심 규칙 (400줄 이내)
├── references/
│   ├── anti-patterns.md  ← 금지 패턴 (단계 3에서 생성)
│   ├── examples.md       ← 좋은/나쁜 예시 쌍
│   └── domain.md         ← 도메인 지식 (필요시)
└── assets/               ← 템플릿 파일 (필요시)
```

메인 SKILL.md는 라우터다. 교과서가 아니다.
"정보를 담는 곳"이 아니라 "정보를 어디서 찾으라고 알려주는 곳"이다.

---

## 단계 5: 스킬 작성

실제 SKILL.md와 참조 파일을 작성한다.

### 작성 규칙

1. **참조 파일의 로딩 트리거는 명시적으로.**
   - ✅ "출력 생성 전에 반드시 references/anti-patterns.md를 읽어라"
   - ❌ "필요하면 anti-patterns를 참고하라" (이건 100% 건너뛴다)

2. **핵심 제약은 파일의 맨 앞과 맨 뒤에 배치.**
   AI는 가장 처음과 가장 마지막에 읽은 것을 가장 잘 기억한다.
   중간에 묻힌 규칙은 무시될 수 있다.

3. **모호한 표현 금지.**
   - ✅ "항상", "절대", "반드시"
   - ❌ "가능하면", "시도하라", "고려하라"

4. **모든 워크플로우 단계는 눈에 보이는 산출물을 만든다.**
   산출물 없는 단계 → 삭제.

5. **검증 게이트를 반드시 포함.**
   스킬의 마지막 단계에 다음 질문을 넣는다:
   - "이 결과물이 스킬 없이 생성한 것과 구별되는가?"
   - "금지 패턴 목록의 항목이 하나라도 포함되어 있는가?"
   - 하나라도 실패하면 재생성.

### SKILL.md 뼈대

```markdown
---
name: [스킬 이름]
description: >
  [트리거 조건을 구체적으로. 어떤 문구에 반응하고, 무엇을 하지 않는지까지.]
---

# [스킬 제목]

## 이 스킬이 하는 일
[한 문단. 무엇을 어떻게 다르게 하는지.]

## 이 스킬이 하지 않는 것
[명시적 제외 범위. 이것이 트리거 오작동을 막는다.]

## 워크플로우
[단계별. 각 단계에 산출물 명시.]

## 금지 패턴
[단계 3에서 만든 목록. 또는 "references/anti-patterns.md를 반드시 읽어라"는 로딩 트리거.]

## 검증 게이트
[최종 출력 전 체크리스트. 실패 시 재생성 조건.]

## 작성 원칙
[이 스킬 고유의 품질 기준.]
```

### 산출물

완성된 SKILL.md + 필요한 참조 파일 일체.

---

## 단계 6: 검증

완성된 스킬을 세 가지 관점에서 점검한다.

### 점검 1: 첫째 원리 (First Principles)

references/review-frameworks.md의 "첫째 원리 점검"을 읽은 뒤 실행한다.

- 이 스킬의 각 구성 요소가 존재할 이유를 증명할 수 있는가?
- 더 적은 부품으로 같은 결과를 낼 수 있는가?
- 제거해도 품질이 떨어지지 않는 부분이 있는가?
   → 있으면 제거한다.

### 점검 2: 실용성

- 실제 사용자가 이 스킬을 매일 쓸 수 있는가?
- 설정이나 입력이 너무 복잡하지 않은가?
- 마찰이 높은 부분은 어디인가?
   → 마찰을 줄이거나, 그 마찰이 품질을 위해 필수적인지 판단한다.

### 점검 3: 차별화

단계 1의 baseline 결과물과 이 스킬의 결과물을 나란히 놓는다.

- 구조가 다른가? (형식만 다르고 내용이 같으면 실패)
- 접근 방식이 다른가? (같은 순서로 같은 것을 나열하면 실패)
- 금지 패턴이 하나라도 남아 있는가? (있으면 실패)

### 산출물

점검 결과 보고서. 문제 발견 시 단계 5로 돌아가 수정 후 재점검.

---

## 단계 7: 배포

### Claude가 할 일

1. 완성된 스킬 폴더 전체를 `/mnt/user-data/outputs/`에 복사
2. 다음을 포함한 설명을 사용자에게 제공:
   - 파일 구조와 각 파일의 역할
   - 트리거 조건 (어떤 말을 하면 이 스킬이 작동하는지)
   - 테스트 입력 예시 2~3개
3. present_files로 전달

### 산출물

완성 패키지 + 사용 가이드.

---

## 진행 중 항상 기억할 것

이 규칙들은 모든 단계에 적용된다. 단계 시작 시와 종료 시 확인한다.

1. **사용자의 말이 재료다.** Claude의 일반 지식이 아니라 사용자가 말한 것에서 스킬을 만든다.
2. **모호함은 적이다.** "좋은 결과물을 만든다"는 지시가 아니다. "오개념 진단 문제가 최소 2개 포함된다"가 지시다.
3. **게으른 버전이 기준이다.** 스킬의 가치는 baseline 대비 차이로만 측정된다.
4. **복잡함은 정당화가 필요하다.** 파일을 추가할 때마다 "이것 없이는 안 되는가?"를 묻는다.
5. **금지 패턴은 계속 자란다.** 스킬을 5회 이상 사용한 후 새로 발견된 패턴을 추가하라고 사용자에게 안내한다.
